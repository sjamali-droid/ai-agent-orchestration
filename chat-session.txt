## What “sub agents” are here

They are **separate agent runs** started via the **Task** tool. Each one gets its own turn to work on a prompt you give it, then returns a single result to the parent agent. They are meant for **bigger or parallel** work (e.g. broad repo exploration, heavy shell work) so the main agent does not do everything in one long chain.

## Types available

| Type | Role (short) |
|------|----------------|
| **generalPurpose** | General research, multi-step work, code search, implementation-style tasks. |
| **explore** | **Read-only**, faster codebase exploration (find files, answer “where does X happen?”). |
| **shell** | Shell/command specialist (git, builds, scripts). |
| **cursor-guide** | Cursor product docs / “how do I in Cursor?” style questions. |
| **best-of-n-runner** | Runs in an **isolated git worktree** (own branch/dir) for parallel attempts or experiments. |

## Important constraints

- **Context is not automatic**: unless you **resume** a prior Task, a new subagent does **not** see the user’s message or the parent’s earlier steps. The parent is supposed to put **everything needed** in the Task prompt.
- **Parallelism**: you can start several Tasks in one message when work is independent.
- **Privacy in chat**: I’m told **not** to cite subagent transcript IDs to you; only parent-level references apply where that rule exists.

Your outline is already coherent: a **Project Manager** owns goals and backlog, specialists own **architecture → build → secure → verify**, and you standardize on **Markdown + MCPs + Context7** for cheap, portable context. Below are focused **tweaks** and **additions** that usually matter when this becomes **multi-repo, multi-team, and installable**.

## Prompt and structure tweaks (Markdown, fewer tokens)

- **Split “prompt” from “state”**: keep `AGENTS.md` / `orchestrator.md` as *stable identity* (name, role, allowed tools, outputs). Put volatile things in `STATE.md` (sprint, WIP limits, current epic, blockers). Parsing is simpler and you avoid re-sending huge prompts.
- **Define a strict handoff schema** between agents (small YAML or JSON block inside MD is fine): `from`, `to`, `artifact`, `path`, `decision`, `open_questions`, `acceptance_criteria[]`. Without this, the PM “knows who is doing what” drifts quickly.
- **One source of truth for backlog**: pick **either** Jira/GitHub Issues MCP **or** Markdown issues—not both without merge rules. Otherwise you get duplicate tasks and conflicting status.
- **Version everything that matters**: `architecture_decision_record/ADR-0001.md`, `contracts/openapi.yaml`, `events/asyncapi.yaml`. The Architect should **produce** these; the Developer should **consume** them; QA should **test against** them.

## Orchestration mechanics (what makes “multi-project” actually work)

- **Project profile** (generated at install time): `project_id`, repos, environments, cloud/K8s cluster name, namespaces, Dapr app IDs, Kafka topics naming convention, secret backend (Vault/K8s secrets), and **non-goals**. This becomes the PM’s top-level context file.
- **Explicit workflow graph**: e.g. `intake → arch_review → implementation_plan → dev → devsecops_gate → qa → release`. Each transition should have **entry criteria** and **exit criteria** (Definition of Ready / Definition of Done).
- **Concurrency rules**: max one active “architecture change” per bounded context; WIP limits per lane; who can override (PM vs Architect).
- **Idempotency for automation**: agents that run terminals/scripts must assume partial failures and retries (especially with Kafka/Dapr).

## Role roster: small but high-impact adjustments

- **Add a “Tech Lead / Integration” hat (can be part-time on Developer)**: owns cross-service contracts, consumer/producer compatibility, Dapr bindings consistency, and “integration seams” the Architect draws but code must honor.
- **Separate “Release Manager” from PM (optional)**: PM owns *what* and *when*; release owns *how shipped* (canary, feature flags, rollback). If you keep one PM agent, spell out release duties inside PM prompt.
- **Security agent scope**: “Sidecars + ACLs + ELK” is good—also add **SBOM**, **image signing**, **policy-as-code** (OPA/Kyverno), and **secrets hygiene** (no secrets in logs). That matches your K8s story cleanly.
- **QA agent**: add **contract testing** (Pact or similar) and **trace-based testing** (OpenTelemetry) if you want integration confidence beyond UI/load tests. For backend-heavy microservices, Playwright alone is often insufficient unless you also define API test layers.

## Stack alignment notes (so prompts do not fight reality)

- **Pub/Sub vs Kafka**: you listed both patterns; pick a default message bus for prompts (**Kafka** or **NATS** or **cloud pubsub**) and treat the other as optional, or you will get inconsistent designs.
- **DAPR**: good—have Architect output **component YAML templates** per capability (state store, pubsub, bindings) and DevSecOps own **scopes, network policies, mTLS expectations**.
- **ELK**: specify whether agents generate **Filebeat/Fluent Bit** sidecar configs vs DaemonSet—this changes manifests and QA’s log assertions.

## Installation UX (clone → configure → run)

- **Interactive wizard outputs** should be *machine-readable* too: `config/project.yaml` + human `README` snippet. Agents should read the YAML first.
- **Bootstrap checklist**: repo access, MCP tokens, cluster credentials (ideally **short-lived**), Context7 library IDs, default branch protections.
- **“Dry run” mode**: plan artifacts without applying cluster changes—huge for safety and faster iteration.

## Real-time visibility (interactive operator experience)

- **Event stream model**: normalize agent outputs to events like `task.started`, `task.progress`, `task.artifact`, `task.failed`, `human.input_required`. Your Next.js UI subscribes (SSE/WebSocket) to a small **orchestrator service** (Express fits) that fans out agent logs.
- **Human-in-the-loop gates**: Architect approvals for breaking changes, DevSecOps gate before prod manifests, PM approval for scope changes—each should emit a `pending_approval` event with a short diff summary.

## Token-saving patterns that still stay safe

- Prefer **summaries + pointers**: “read `docs/adr/ADR-0012.md` section ‘Kafka topics’” instead of pasting large manifests repeatedly.
- **Tool allowlists per agent**: PM should not run cluster apply; DevSecOps should not rewrite product requirements; reduces accidents and prompt bloat from defensive instructions.

## Suggested edits to your agent definitions (minimal wording changes)

- **Software Architect**: add outputs: **C4 + sequence diagrams**, **data ownership map**, **topic/schema contracts**, **K8s/Dapr baseline**; add “non-functional requirements”: SLOs, latency budgets, retention.
- **Developer**: add “implementation must reference ADR + OpenAPI/AsyncAPI paths”; add test expectations per feature.
- **DevSecOps**: add supply chain + policy + secret management + pipeline gates.
- **QA**: define **test pyramid** responsibilities (unit owned by dev, integration/contract/load owned by QA) so scope does not blur.

Great question. Let me explain why these contracts matter in this orchestration system.

## What OpenAPI contracts are

They are a **machine-readable specification** of every API endpoint before any code is written. They define:

- **Routes** (e.g. `POST /auth/login`)
- **Request format** (what fields the body must have, their types, which are required)
- **Response format** (what the JSON response looks like, status codes)
- **Auth requirements** (which endpoints need a JWT)
- **Validation rules** (max string length, allowed enum values, file size limits)

## Why we need them in this orchestration

**1. Architect and Developer speak the same language**

The Architect designs the API shape. The Developer implements it. Without a contract, the Developer guesses what fields to return, the frontend guesses what to send, and things break at integration time. The contract eliminates that.

**2. Multiple agents work in parallel without drift**

Right now, the Developer agent will build the backend against these contracts. A separate Developer task will build the frontend against the same contracts. The QA agent will write contract tests that validate responses match these specs. If everyone reads the same YAML, they stay in sync without constant back-and-forth.

**3. Contract tests catch breaking changes**

When the Developer changes an endpoint, the QA agent (ISSUE-0071) runs contract tests that compare actual API responses against these YAML specs. If the response no longer matches, the test fails before it reaches production. This is much cheaper than finding the bug in a full E2E test.

**4. Code generation is possible**

From these contracts, tools can auto-generate:
- TypeScript types for the frontend
- Request validation middleware for Express
- API client SDKs
- Postman/Insomnia collections for manual testing

**5. This is the "contracts before code" principle (§1.4)**

From the master spec: *"no implementation without linked OpenAPI / AsyncAPI"*. The contract is the **agreement** between services. It is the equivalent of an interface in code, but for HTTP.

## Concrete example from your project

Looking at `auth-service.openapi.yaml`:

```yaml
/auth/register:
  post:
    requestBody:
      schema:
        required: [name, email, password]
        properties:
          name: { type: string, maxLength: 255 }
          email: { type: string, format: email }
          password: { type: string, minLength: 8 }
    responses:
      "201":
        schema: { $ref: "#/components/schemas/AuthTokens" }
      "409":
        description: Email already exists
```

This tells the Developer agent **exactly**:
- The route is `POST /auth/register`
- The body **must** have `name`, `email`, `password`
- Password must be at least 8 characters
- On success, return an `AuthTokens` object (access_token, refresh_token, expires_in)
- On duplicate email, return 409

No ambiguity. No Slack messages asking "what should register return?".

## OpenAPI vs AsyncAPI

| | OpenAPI | AsyncAPI |
|---|---|---|
| **For** | HTTP request/response APIs | Kafka/pub-sub event messages |
| **Example** | `POST /tasks/:id` | `tasksphere.task.created` event |
| **Who produces** | Architect | Architect |
| **Who consumes** | Developer, QA, Frontend | Developer (producers), notification-service (consumer), QA |

Both serve the same purpose: a **written agreement** that prevents drift between agents working in parallel.
